# Qualify a saved research run

Use this workflow across project stages. Select checks by the requested outcome, implemented capabilities and available evidence, not by a stage number. A later stage adds its own scientific or operational acceptance criteria; this skill does not replace them or certify an entire stage from one run.

This is a Codex development workflow, not a runtime rule for scientific peers. Preserve the selected provider, model, reasoning settings, credential profile and each attempt's lineage. Record authorized changes explicitly rather than applying an old default to a different run. The host owns mechanical resources; peers choose scientific work and may continue after a report appears. Do not impose a scientific turn limit, consensus gate, or arbitrary call or research budget.

## Select the evidence and runtime

Read current `AGENTS.md`, `README.md`, setup and the relevant runtime, state and provenance documentation. Identify the requested task and acceptance criteria, exact workspace/state location, run and parent/follow-up identities, observation time, and whether the evidence is live, saved live work, replay or a fixture. Compare current checkout, loaded host build and saved attempt configuration. A passing local check does not prove which bytes the host loaded.

A denied process or localhost probe means availability is unknown, not that the host stopped. Verify through an allowed process check and authenticated read-only endpoint before restarting or launching a replacement; do not create a duplicate host to bypass an inspection restriction.

For the repository's mission/SQLite runtime, read [mission runtime inspection](references/mission-runtime.md) before using its commands or receipt helper. The reference owns their prerequisites and supported record shapes. If that runtime or helper is absent or incompatible, skip those commands and use the selected runtime's documented read-only records; do not abandon the review or infer support from this skill package. For another runtime, first establish its command and record mapping without guessing endpoints or schemas. Produce a private manual receipt when no compatible helper exists, stating what it could not measure.

Check other active runs and shared provider capacity before calling a result isolated. An unavailable component limits its own proof. Mark a dimension **not applicable** only when the task does not require it; required but absent evidence remains **missing**, not a pass. For example, a retrieval-only case has no model-token result, while a peer-collaboration test with no peer records lacks required evidence.

## Inspect before another test

Before choosing the next case, check whether local defaults limit the broader research goal. Separate verified provider/context constraints from transport safeguards and unqualified convenience limits. Inspect requested versus returned passage sizes, access to later search hits and source pages, and whether consecutive model inputs actually receive the requested evidence. Prefer a complete abstract or coherent section when the complete request fits; preserve model-selected smaller windows and exact continuation when it does not. Exercise a meaningful larger variation offline before expanding live work. A saved passage is not proof of model delivery, repeated successful reads are not necessarily progress, and fewer calls are useful only when evidence fidelity and task completion are preserved. Correct evidenced restrictions within the authorized scope; record genuine constraints and untested alternatives without turning qualification into a scientific gate.

1. **Reconcile execution.** Produce a private receipt using the compatible helper or saved records. Separate prepared intents, pre-dispatch markers, captured responses, usage-bearing responses, tool outcomes and accepted task outputs. A dispatch marker is not proof of provider execution or billing. Distinguish local rejection, HTTP error, failed capture, unknown outcome and provider wait. Reconcile runner manifests, observations, calls and snapshots when present. Keep absent fields and unproven lineage unknown rather than zero.
2. **Evaluate context, calls and latency.** Compare useful evidence and accepted outputs with input/completion tokens, optional cache/reasoning subsets, corrective turns, repeated work and continued consumption. Inspect exact intent/input-inclusion records to distinguish necessary instructions, task state, tools and source passages from duplicated source text, repeated own outcomes or unrelated history. Judge them against task complexity and a declared comparable baseline, not aggregate token totals alone. Separate active work, queue/provider waits, total elapsed time and time to first useful evidence/output. Do not add cache or reasoning subsets to totals that already include them, invent reasoning usage, or claim a latency improvement without comparable observations.
3. **Diagnose failures and recovery.** Find the first divergence before its downstream symptoms. Distinguish shared request/token capacity from a request too large to fit, an invalid tool selection, a tool/data failure or an uncertain external effect. Check provider headers and saved wait state when available; do not infer quota independence from different keys. Verify that repair changes the faulty request, preserves useful work and avoids duplicate accepted effects. Inspect context freshness, compaction, configuration continuity and recovery after interruption where relevant. Missing restart evidence cannot establish hours-long persistence.
4. **Evaluate evidence and collaboration.** Check exact source copies, distinct publication/study identities, inspected passages, citations and counterevidence. A citation pointer does not establish claim support, and a source-copy count does not establish search coverage. Inspect local rejections, missing tool results and successful effects separately. For peer work, identify sender, recipient or shared audience, timestamps, requests/replies and whether the requester actually used the contribution. For experiments or analyses, inspect available input/data versions, execution artifacts, outputs and reproducibility records against that task's criteria. Tool completion, accepted output and scientific validity are different outcomes.
5. **Evaluate persistence and human review.** When growth or persistence is in scope, compare before/after logical references, unique referenced objects and physical/database sizes separately. Account for shared objects, observation duration and concurrent work; missing metadata leaves totals incomplete. Do not delete history to improve a measurement. Review the same saved run's output, activity, communication and exact source/task/attempt links in the user-selected interface; use `$os-review-atlas` for implemented Atlas surfaces. Keep findings readable and diagnostics separate. A recorded screenshot or a passing component test is not proof of current UI behavior.
6. **Conclude before another test.** Write a concise private per-run or batch conclusion: **outcome; first mismatch and supported cause or hypothesis; exact supporting run/record references; next discriminating check**. Include the observation boundary, continuing or unknown work, applicable criteria and unmeasured dimensions. Before repeating a live test, document the diagnosis and changed hypothesis or implementation, what the next test resolves and its comparison conditions. Use offline fixtures or saved replay when they answer the same question. This development review does not pause scientific peers or cap their lifetime.

Follow applicable evidence in order: request and selected run → saved task/attempt → prepared intent → dispatch and captured response → tool result → source and peer use → accepted output → reader presentation. Mark consequential claims **verified**, **inferred**, **missing** or **inconsistent**. Lead with the first layer that diverged and name its downstream effects. Keep execution, scientific usefulness and visible presentation separate. Expand exact records only where a discrepancy warrants it so the diagnosis stays readable.

Live qualification needs the user's explicit prior authorization for provider calls; existing authorization remains valid within its stated scope. Use only the selected runtime's verified activation and overlap controls. Do not start, resume, cancel or submit live work merely to make a receipt. Never silently switch provider, account, model, reasoning settings or auth mode. Keep raw prompts, source bodies, private returned reasoning, credentials and personal identifiers out of summaries and tracked files.

Report offline checks, saved-record evidence, live calls actually authorized and observed, UI evidence, and continuing or unknown work as separate proof layers. Give exact run IDs only in the private receipt or appropriately private handoff. The receipt is a diagnostic aid, not a scientific acceptance score or billing statement.
