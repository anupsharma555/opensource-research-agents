## Inspect before another test

1. Identify the exact state directory, workspace/build, run IDs, parent/follow-up links and observation time. Use `scripts/dev mission status --state-dir DIR --run-id RUN_ID` and, when needed, `scripts/dev mission calls --state-dir DIR --run-id RUN_ID`. These commands read saved work without dispatching it. Check other active runs before calling a result isolated.
2. Produce a private receipt from the saved SQLite store. From the repository root: `.venv/bin/python .agents/skills/os-qualify-run/scripts/receipt.py --state-dir DIR --run-id RUN_ID` (repeat `--run-id` for an explicitly parallel batch). It writes one mode-0600 JSON under ignored `.local/checks/` and prints only its path. Inspect it privately. It uses a WAL-aware read-only SQLite transaction, record metadata and only small exact linked tool-result blobs to classify outcomes; it never reads source, model or snapshot blobs. If a field is absent or lineage cannot be proven, keep it unknown. The receipt counts prepared calls, dispatch markers, captured responses, usage-bearing responses and saved tool outcomes separately; a marker proves the saved pre-dispatch boundary, not provider billing. Its storage totals separate referenced object bytes, saved snapshot bytes, control revisions and whole-store database files. It never scans all object bytes.
3. Reconcile the receipt with the qualification runner's `manifest.json`, `qualification-status.json`, per-case `observation.json`, `last-state.json`, `calls.json` and saved snapshots, if present. The runner's observation window is not mission termination. A run can be `completed` while `continuingTaskIds` or other host work still consumes resources. Failed capture, HTTP errors, unknown usage, quota waits and accepted outputs are distinct. Treat call records with raw responses as private.
4. Check exact source copies, distinct publication identities, inspected passages, citations and counterevidence before judging an answer. The receipt's source-copy counts cover referenced copies, not every discovered or inspected copy; inspect retrieval and source-inspection records before claiming coverage. A linked citation establishes a recorded pointer, not claim support. Inspect peer requests, replies and whether the requester used them; count tool completion separately from accepted reports and from scientific validity. The receipt's saved tool-result statuses do not prove every attempted tool action: drill into `mission calls` and exact task records for local rejections, missing result records and successful effects. For efficiency, compare useful evidence and accepted outputs to actual dispatched calls, provider input/completion tokens, optional cache/reasoning subsets, repeated source or own-outcome text, errors and continued consumption. Diagnose the cause of excess input or retries using exact call/intent/inclusion records; do not infer it from aggregate tokens alone.
   Judge prompt components, call count, and active versus waiting time against the complexity of the requested research; this comparison does not impose a scientific call or lifetime cap.
5. Write a concise private per-run or batch conclusion: what was observed, the first divergence, evidence and uncertainty, the current hypothesis, one change or proof step, and what a further live test would resolve. Use a short handoff shape: **outcome; first mismatch and supported cause or hypothesis; exact supporting run/record references; next discriminating check**. Before repeating a live test, document the diagnosis and changed hypothesis or implementation. Use offline fixtures or saved replay when they answer the same question.

Work through the evidence in order: request and selected run → saved task/attempt → prepared intent → dispatch and captured response → tool result → source and peer use → accepted output → reader presentation. At each layer mark a consequential claim **verified**, **inferred**, **missing** or **inconsistent**. Lead with the first layer that diverged, then name its downstream effects. Compare current checkout and loaded host-build identity with the saved attempt configuration; a passing local check does not prove the active host loaded those bytes. Keep execution, scientific usefulness and visible presentation as separate outcomes. Expand exact records only where the concise receipt reveals a discrepancy, so the diagnosis stays readable.

Live qualification needs the user's explicit prior authorization for provider calls. The existing runner `scripts/qualify_stage4_mission.py` requires `--allow-live`; it defers new submissions while work remains unless the operator deliberately passes `--allow-overlap` for a parallel batch. Neither option changes agent lifetime. Do not start, resume, cancel or submit live work merely to make this receipt. Never silently switch provider, account, model, reasoning settings or auth mode. Keep raw prompts, source bodies, private returned reasoning, credentials and personal identifiers out of summaries and tracked files.

Report offline checks, saved-record evidence, live calls actually authorized and observed, UI evidence, and continuing or unknown work as separate proof layers. Give exact run IDs only in the private receipt or appropriately private handoff. The receipt is a diagnostic aid, not a scientific acceptance score or billing statement.
