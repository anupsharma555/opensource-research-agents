# Task planning

Planning is an optional aid to the assigned task. Use it when uncertainty, several plausible next actions, or collaboration would benefit from a saved checkpoint. Match its detail to the question: a simple supported answer may finish directly, and a small task may need only a goal and next action. Any role may plan its own task; there is no compulsory planning peer, mandatory research sequence, consensus gate, or fixed number of revisions.

Choose the content that helps the next decision. A goal can describe the question and what useful completion would establish. Uncertainties can name unresolved interpretations or missing evidence. Next actions can distinguish intended work from work already dispatched or observed. Dependencies can record the exact peer request, work proposal, or retained result on which a decision depends. Evidence and peer feedback can explain why a direction changed. Dissent, counterevidence, negative results, limitations, and a completion or pause condition help prevent an unproductive direction from being presented as settled. These are conceptual fields; the attached tool schema owns the accepted structured content.

Use `save_plan` and `read_plan` to checkpoint structured intent in one task/actor working note. The host validates the content, enforces ownership, and requires the exact current revision when replacing it. Keep returned revision references, read the current checkpoint when recovering context, and revise against the version actually inspected. A stale-revision rejection should lead to inspecting the current revision and deciding whether the proposed update still makes sense. An ownership rejection does not authorize overwriting another actor's checkpoint. Preserve saved history; do not silently erase a peer's disagreement or a previous negative result to make the plan look successful. The plan tools provide durable revision checks beyond prose; their receipts establish saved state, not scientific validity or executed actions.

The existing work and communication tools remain authoritative. Use `propose_work` or `revise_work` for actual work proposals and scope changes. Use `peer_request` for a directed request and its established reply mechanism for responses. Use `wait_for_dependencies` when progress depends on existing work or messages. An intention or dependency written into a plan does not dispatch a task, send a message, grant a tool, or create a wait. Notes remain available for findings, context, and explanation. Planning adds no independent scheduler, approval gate, or narrowed tool set.

Replanning should follow a meaningful change: inspected source text challenges an interpretation, a peer identifies a design limitation, a dependency completes or becomes unavailable, or a negative result makes an alternative useful. Explain the problem, alternatives, evidence, trade-offs, and observable next check. Preserve source IDs, versions, locators, hashes, and access limitations where relevant. Distinguish a discovery lead from inspected evidence, and retain counterevidence rather than resolving dissent by assertion. No private model reasoning is needed to explain a decision.

Complete with a supported result when the task's useful outcome is established. A useful pause can name the current finding, remaining uncertainty, blocking dependency, and condition that would make further work worthwhile. A pause, absent source, or negative result is not automatically failure; neither is it proof of completion. Avoid serial plan edits that merely restate the same intention. While a dependency is pending, use the existing wait path without extra calls just to maintain the checkpoint. After repeated replanning without new evidence or progress, flag a host churn diagnostic with observable revisions and unchanged dependencies. Keep that diagnostic separate from findings: it does not impose a global research cap, cancel other branches, or choose scientific interpretations for peers.

The synthetic example illustrates decisions rather than a valid tool payload. Offline package tests establish registration, pinning, optional activation, and helper absence. They do not demonstrate model planning quality or a live research mission.
