# Stage 3 queued-work burst measurement

ANU-438 measured the existing executor with disposable SQLite stores and controlled synthetic callbacks on 2026-10-08. The checked-in workload is `scripts/measure_stage3_bursts.py`; the final-source private receipt is `.local/stage3/extensions/bursts/run-d98213474d1f/measurement.json` (8, 24 and 96 work items). It contains exact SHA-256 identities for the script and five inspected runtime files. The measured executor hash was `075088d99121576aac3ca89e93b53935a85b6a2be6a927332f5fe4dcfddc3eaf`; the capacity hash was `b8f173e6eb5b3355b00e030fb07c8556bb8ae5c5d10e3feaa374d08b98225bc7`; the script hash was `bf2c12336041441c81021c5780b731096c030aab60fb993e7a5ca68b64ac8f72`. The source hashes were checked again after the run and matched its receipt. These source identities are uncommitted checkout bytes, not a claim that Git HEAD alone reproduces the run.

The executor saves each work intent in `StateStore`, scans the durable board and work records, and holds only admitted callbacks in its local active set. It has no separate in-memory writer queue. `run_ready` rescans after a callback finishes or a same-process submission notifies it; the capacity ledger admits model and retrieval work under separate permits. `_prepare` pages stored work but materializes the mission's work and eligible set while scanning. This is inspected behavior (`src/ora/coordination/executor.py`); the table below measures the selected workload, not a general growth bound. No production queue or provider was used.

The input is identical across each serial/eligible-parallel pair: one fast model task, one model callback delayed by 0.5 seconds, one independent retrieval task, one dependent on the fast task, ordinary model tasks to reach the declared size, and one queued task canceled during execution. Every task pins one of the same three saved synthetic agent-configuration references in both arms. Model permits are the only changed setting: one or three; retrieval has one permit in both. A second `run_ready` call races the first as a duplicate readiness notification. The StateStore and executing host are reconstructed after submission; a later fresh host replays the notification after completion. These are reopen tests, not process kills. Each accepted-result transaction receives an **intentional 1 ms delay after writing its records and before SQLite commit**, while its transaction lock is held. This is a controlled writer-pressure input, not an observed storage defect. The workload has no provider calls, model reasoning, scientific task cap, or fixed mission duration.

Measured on macOS 15.5 arm64 with pinned Python 3.12.12; each arm ran in a fresh process and disposable state directory. Times below are one run per arm, rounded. RSS is the process **high-water** resident set after setup → after execution (MiB); it includes interpreter, imports and fixture setup, and does not isolate Python heap or executor allocations. WAL is the largest sampled file size at 20 ms intervals (MiB), so shorter peaks may be missed. The `active` count includes callbacks, including the separate retrieval lane, but excludes queued and acceptance work.

At all three sizes, every noncanceled callback executed and committed once; the canceled callback did not run. The duplicate readiness call and post-run reopen produced no additional accepted work. One canceled proposal remains visible as an open board item, but its capacity operation is `canceled` and no capacity-runnable work remains. The retrieval contribution committed while the slow model callback was still active, including with one model permit. An immediate separate-connection read saw every accepted result; the p95 query duration was 0.54–0.79 ms across arms. That duration measures a local visibility check, not application refresh time. The resulting database files were about 0.39, 0.91 and 3.27–3.32 MB for the 8, 24 and 96 work-item arms respectively.

For the 96-item arms, the sum of saved per-work elapsed / dispatched-active / capacity-queue wait was 698.0 / 1.26 / 696.4 seconds with one model permit and 325.6 / 6.00 / 318.9 seconds with three. These are overlapping task totals, not run wall time. The active interval is dispatch to acceptance and can include event-loop scheduling or writer delay; it is not isolated callback CPU or provider time. Quota, provider-capacity and retry waits were zero in this fixture. The p95 accepted-result transaction duration, including the injected 1 ms hold, was 4.37 and 4.56 ms in the two 96-item arms.

The dependent began before the unrelated slow callback ended in the 8- and 24-item eligible-parallel arms. In the 96-item arm it began at 5.91 seconds, after its parent committed at 1.18 seconds and the slow sibling ended at 2.85 seconds; 94 contributions committed before that child. It was retained and completed, so this was queued delay rather than an all-peer barrier or lost work. The capacity scheduler orders older eligible work ahead of a newly unblocked dependent with otherwise equal lane priority. A priority override could favor one scientific branch without evidence that it is more useful. The executor also synchronously scans durable work and admission records as the backlog grows; its contribution to the 96-item delay is plausible from source inspection but was not isolated by this measurement.

The measured decision is **no additional executor change needed for this burst workload**. At these declared sizes, local active callbacks stayed within permits, durable work survived duplicate notifications and restart, cancellation was observable, and an independent route made accepted progress. The first accepted result was not consistently faster with more model permits, even though total elapsed time was lower in these individual parallel arms. Larger realistic workloads or a traced scan profile may justify a targeted change later. Do not infer an SLA, production throughput, scientific-quality improvement, multi-host account admission, or ten-hour recovery from this fixture. The receipt's per-task elapsed and active/wait sums overlap across concurrent work; they are distinct from wall time. No quota or provider wait was injected, so those categories are zero here.

Reproduce after `scripts/dev setup` using the pinned project interpreter. Each command creates fresh ignored local state and a JSON receipt; pass a new `--output-dir` only when a specific private location is needed.

```sh
.venv/bin/python scripts/measure_stage3_bursts.py --sizes 8,24,96 --slow-seconds 0.5 --commit-delay-seconds 0.001
.venv/bin/python -m pytest tests/coordination/test_burst_workload.py
```

The later complete-loop and endurance work can reuse this workload and add authorized real provider, longer queue-window, and client-refresh observations separately. A later change to executor result-acceptance semantics requires rerunning this receipt against the new source identity before treating these numbers as current.
