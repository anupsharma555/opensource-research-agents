# Foundation implementation strategy

The first release establishes interfaces, test scenarios, a sample desktop client,
and reproducible development. It does not claim that a scientific research mission
has run autonomously. Every result identifies whether it came from a synthetic
fixture, a framework experiment, a model call, or the actual application.

## Boundaries and order

1. Define independent benchmark packets, component ownership and storage behavior.
2. Specify one canonical set of commands, events and read models. Generate the
   client types; test repeated delivery, stale changes and recovery independently
   of any orchestration library.
3. Connect reusable skills to role manifests, demonstrate attempt-private state,
   and expose thin development commands over those shared modules.
4. Build a React Mac prototype from clearly labeled sample research artifacts.
   Keep readable findings separate from operational diagnostics.
5. Compare runtime adapters under the same scripted peer behavior. Use the result
   to select a starting boundary, not to claim a universal framework winner.
6. Verify a private Git round trip, clean installs and the actual cloud development
   environment. Native Mac behavior and cloud development have separate evidence.

Work can proceed in parallel through these interfaces. Integration prerequisites
identify the input that must exist for a test, not a reason to freeze unrelated
work. Scientific peers choose questions, tools, interpretations and follow-ups;
the host handles durable writes, eligibility and resource ownership.

## Preservation and compatibility

Existing classifier examples remain available. Local credentials, old run outputs,
personal conversation references and private project-management snapshots stay
outside version control. This is an unreleased interface: change it directly,
regenerate derived types, and record the version's effect on stored records and
active work. Do not add compatibility machinery without an actual consumer.

## How decisions remain explainable

Decision records state the problem, considered alternatives, selected approach,
evidence, trade-offs and what would change the decision. Tests explain the behavior
being established and distinguish mechanical validity from scientific quality.
Agent-facing instructions request concise, source-linked decision summaries and
next actions. Raw private reasoning is not required to understand or audit a result.

## Verification

Run the smallest behavioral check after a change, then the shared offline suite
before integration. Generate schemas and types from their source and fail with an
actionable diff if they drift. Test a deliberate malformed input, an interrupted
operation and an unaffected sibling. Record the exact commit, toolchain and proof
boundary for clean-clone, native app and cloud checks. Never replace a missing live
check with a fabricated fixture receipt.
